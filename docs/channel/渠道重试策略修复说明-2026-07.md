# 渠道重试策略修复说明（2026-07）

针对"渠道 A 出错后不重试 B/C、错误直接返回客户端"的审计结果，落地了 5 项修复。
本文是行为变化清单（发布说明素材），设计冲突分析见审计记录。

## 修复清单

### ① 渠道配置错误恢复切换（去 SkipRetry）

`model_mapping` 解析失败/成环、`param_override` 非法这两类 `channel:` 前缀错误
不再标记 SkipRetry，按"渠道错误必重试"语义切换下一渠道（全部 relay 格式，共 19 处）。
`ConvertRequestFailed` / `InvalidApiType` 等用户输入可触发的错误仍保留 SkipRetry。

**行为变化须知**：
- 开启 AutoBan + 自动禁用时，一次请求可能连环禁用多个配置错误的渠道（此前每请求最多 1 个）——属预期，配错渠道应退出轮询并通知管理员。
- 全部渠道都配错时可触发计划降级/钱包回退（受计划 AutoSwitch 门控），客户端错误从具体的 `unmarshal_model_mapping_failed` 变为最后一次真实错误或耗尽消息；管理员仍可在错误日志按 `error_code=channel:model_mapped_error` 定位。

### ② 上游 400 的渠道特有错误按规则切换

- **种子规则**（首次启动播种一次，可在"渠道故障转移规则"页停用/修改，删除不复活）：
  - `内置：Gemini 无效密钥 400 切换渠道`（关键词 `api key not valid` / `api key expired`）
  - `内置：Anthropic 余额不足 400 切换渠道`（关键词 `credit balance is too low`）
- **规则匹配输入修复**：上游响应体不可解析（HTML 错误页等）时，规则匹配文本
  （含原始 body）随错误对象贯穿整条链路（`NewAPIError.RuleMatchInput()`），
  shouldRetry / 健康记录 / 同渠道重试规则不再因消息截断而失配。
- **禁用护栏**：仅由用户规则升级的 `channel:upstream_error` 不再走
  `ShouldDisableChannel` 的直通禁用（兑现规则"只临时暂停、不永久禁用"契约）；
  硬编码状态码升级（401/403/429/5xx）的直通禁用行为不变，
  自动禁用关键词表（如 Anthropic 欠费文案）仍独立生效。
- 新增关键词规则时**严禁泛化词**（如 `quota`、`api key`），会误伤换渠道无解的用户级错误。

### ③ 耗尽时返回真实上游错误

所有渠道尝试失败后，客户端拿到的不再是"获取可用渠道耗尽 (get_channel_failed) 500"，
而是最后一次真实上游调用的错误（状态码、错误体）。替换仅发生在渲染期，
跨计划/钱包降级门控的输入与此前逐位一致。运维告警若匹配"渠道耗尽"文案，
注意迁移到日志侧（`LogError` 仍保留耗尽记录）。

### ④ 流式/伪 200 错误检测（不重试 → 报错可切换）

以下场景此前一律按"成功"处理（计费 + 记渠道健康成功 + 客户端拿到空响应或错误 JSON）：

| 场景 | 现在的行为 |
|---|---|
| 上游 200 后零事件断开（OpenAI/Claude 流） | `empty_response` 500，可切换渠道，不计费 |
| 首包超时（STREAMING_TIMEOUT）零事件 | `empty_response` 504（保守语义：记健康、剩余额度内切换） |
| 流内 `data: {"error":{...}}` 伪 200 错误块 | 解析为上游错误，改写 500 可切换，不转发错误块 |
| 非流式伪 200（含 Azure 风格无 `type` 的 `{"error":{code,message}}`） | 识别并改写 500 可切换（仅在无 choices 时判错，避免误伤） |
| /v1/responses 流 `response.failed` / `error` 事件 | 按错误处理（此前被吞掉或伪装成 `finish_reason=stop`） |

错误码一律**非** `channel:` 前缀，避免单次抖动经 `IsChannelError` 直通触发永久禁用，
渠道下线仍由健康滑动窗口（30% 失败率阈值）兜底。伪 200 的改写状态码按错误内容映射：
数字型 code 直接采用（保留 429 等原生语义）；内容过滤/上下文超限等用户请求问题归 400
（不重试、不给渠道记失败）；其余 500 可切换。零事件请求从"按 prompt tokens 计费"变为
"不计费+预扣返还"；流中途（已转发内容后）出现的错误块按"截断的成功流"收尾并对已输出
文本正常计费（此时无法重试，退款反而造成漏计）。
若个别代理渠道存在"空流即成功"的合法行为，可配置 error_type=client 规则
（匹配 `empty_response`）豁免健康记失败。

**全局"已写响应即放弃"守卫**：业务字节（SSE 数据/响应体）一旦写回客户端，
跨渠道重试、跨计划降级、钱包回退全部停止（此前外层循环无此守卫，存在双写风险）；
最终错误对已写流以 SSE error 事件收尾而非 `c.JSON`。
仅写出过 ping 注释不算业务字节，仍可安全切换。

### ⑤ warning 渠道关骰补扫

warning 状态渠道默认 80% 概率被跳过（降流量探测），同优先级 B/C 可能双双被
掷骰跳过（64% 概率）导致"渠道明明存活却报耗尽"。现在：**所有优先级耗尽且本请求
曾有渠道仅因掷骰被跳过时**，关闭掷骰从最高优先级补扫一遍（首选路径与重试路径对称）。
常态下的 20% 探测流量比例不变；补扫命中的渠道若继续失败，健康系统照常累积并升级为
suspension（完全跳过），无雪崩风险。

## 已知限制

- DB 模式（`MEMORY_CACHE_ENABLED=false`）下渠道排除机制仍未实现（`model/channel_cache.go` 回退路径的 TODO），重试可能反复选中刚失败的渠道。建议生产开启内存缓存。
- 开启 ping 时，若有未经标记的直写路径先于 ping 写出业务字节，守卫会保守禁止重试（宁可少重试也不双写）。

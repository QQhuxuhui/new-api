# 两渠道 Claude 真假检测差异分析

抓包点：loopback `lo:3010`（Caddy→sub2api 明文HTTP段），tcpdump 纯旁路。
- 渠道A（官方订阅，满分）：`chanA_20260530-000225.pcap`，7 个 POST /v1/messages
- 渠道B（真模型，38分）：`chanB_20260530-000623.pcap`，9 个 POST /v1/messages

## 结论先行

两个渠道返回的 `model` 都是真的 `claude-opus-4-6`，回答也都是真实推理。
**差异不在模型本身，而在响应"信封(envelope)"**：

- **渠道A = 原生第一方 Anthropic API**（`msg_` 开头的 id、有 ping、有完整 usage 字段）
- **渠道B = 经 Google Cloud Vertex AI 转发的 Claude**（`req_vrtx_` 开头的 id 是铁证）

检测站打的就是这些"信封指纹"，B 每一项都对不上 → 38分。

## 前提与已排除项（保证归因干净）

- **两渠道收到的请求完全一致**：A/B 的 7~9 个 POST /v1/messages 请求体大小是同一套
  （98682 / 97899 / 98324 / 829 / 98182 / ~100k / 98674），User-Agent 都是
  `claude-cli/2.1.153`、同样的 Anthropic-Beta / Anthropic-Version 头。
  → 检测站对两边发的是相同的题，差异只可能出在**响应**，归因干净。
  （B 多出几条 98674 的重复请求 = 检测站对 B 多跑了几轮/重试，不影响对比。）
- **已排除"响应头差异"这个红鲱鱼**：上游真正的 `anthropic-*` 响应头（ratelimit、
  request-id、organization-id 等）被 sub2api 在两个渠道上**同样地抹掉并替换成自己的头**
  （CSP / X-Request-Id 等两边一致）。所以分差不在 HTTP 头，而在 SSE 响应体。
- 两渠道用的是不同的 sub2api API key（A: `sk-ec5b41…`，B: `sk-a525065…`），即两条独立渠道。

## 逐项铁证

### 1. 消息 ID 前缀（最致命）
| | message id |
|---|---|
| A | `msg_01GTX6dKkgZCKKHN44J9mDD5` ← 原生 Anthropic |
| B | `req_vrtx_011CbXn5ozhRPp6QwJVFUquZ` ← **Vertex AI 请求ID** |

`req_vrtx_` 是 Google Vertex 平台的请求标识前缀，一眼就能被检测站判定为非原生。

更糟的是 **B 的 id 格式连自己都不统一**：除 `req_vrtx_…` 外，还出现裸 id
`Mioaau7HHYakqtsPjNSO4QY`（无任何前缀，非 `msg_` 非 `req_vrtx_`）——说明 B 这条链路
经过了不止一层改写，原生 `msg_` id 已被彻底丢失。

### 2. usage 字段缺失一大片
渠道A 的 message_start.usage：
```json
{"input_tokens":743,"cache_creation_input_tokens":25100,"cache_read_input_tokens":0,
 "cache_creation":{"ephemeral_5m_input_tokens":25100,"ephemeral_1h_input_tokens":0},
 "output_tokens":1,"service_tier":"standard","inference_geo":"not_available"}
```
渠道B 的 message_start.usage：
```json
{"input_tokens":25543,"output_tokens":1}
```
B 缺：`cache_creation_input_tokens`、`cache_read_input_tokens`、`cache_creation`、
`service_tier`、`inference_geo`、`output_tokens_details.thinking_tokens`。

### 3. SSE 没有 ping 事件
- A：事件流含 `event: ping`（原生 API 周期性心跳特征）
- B：**0 个 ping**

### 3b. message_delta 高级用量字段全缺
渠道A 的 message_delta.usage 还带这些（实测计数：`iterations`×3、`server_tool_use`×2、
`thinking_tokens`×2），其中 A 有一轮真实触发了 `server_tool_use:{web_search_requests:1}`：
```json
"output_tokens_details":{"thinking_tokens":1783},
"server_tool_use":{"web_search_requests":1,"web_fetch_requests":0},
"iterations":[{...}]
```
渠道B 的 message_delta.usage **完全没有** `iterations` / `server_tool_use` /
`output_tokens_details`，只有 `input_tokens`+`output_tokens`。

### 4. 缺 stop_details 字段
- A：message 和 message_delta 都带 `stop_details`
- B：完全没有该字段

### 5. JSON 字段顺序不同（被重新序列化的痕迹）
- A：`model, id, type, role, content, ...`（原生固定顺序）
- B：`content, id, model, role, ...`（字母序，说明被某层 SDK/代理重新打包过）

### 6. Prompt 缓存完全失效（既是指纹，也是真金白银的成本问题）
- A：后续轮次 `cache_read_input_tokens: 25078`，缓存命中，省钱
- B：每一轮 input_tokens 都是 ~25000 全量重读，**从不命中缓存**
  → 不仅被检测站扣分，你的 token 成本也比 A 高出数倍

## 检测站为何给 38 分
检测站逐项核对原生指纹：id 前缀、service_tier、cache 字段、ping、stop_details、
字段顺序。B 经 Vertex 中转，以上指纹全丢，所以只能拿基础分（模型答对内容的部分）= 38。

## 可选方向（诚实版）
1. **换原生 API 上游**：该渠道改用第一方 Anthropic API 的供货源，指纹自然全对（A 已是）。
2. **认清 B 的真实代价**：Vertex 渠道不止丢分——无缓存导致成本显著偏高、缺扩展思考用量等特性，
   即便不看检测站，长期用也吃亏。
3. 若只是想给客户一个"真"的来源，最干净的是直接用原生通道，而不是改写响应去伪装来源
   （那会误导依赖检测的下游，且 Vertex 的能力差异是真实存在的，伪装不掉缓存/特性的缺失）。

# 数据附录（供程序化差异分析）

字节级精确导出（tshark `--export-objects`，已规避文本转义问题）。两渠道各一套，
位于 `/root/captures/export/A/`（原生）与 `/root/captures/export/B/`（Vertex）。

## 文件清单（每个渠道目录内）
| 文件 | 内容 | 用途 |
|---|---|---|
| `responses.sse.txt` | 每个 /v1/messages 响应的**完整原始 SSE**（真实换行，按时序，含分隔头） | 人读 / 整体 diff |
| `events.jsonl` | 逐 SSE 事件解析，每行一个 `{ch,resp,seq,event,data}` | **程序对比主力**：可按 event 类型、字段、顺序逐条比对 |
| `requests.jsonl` | 每个请求体解析（model/max_tokens/stream/thinking/tools_count/top_keys/system_preview） | 核对两边输入一致 + 配对 |
| `schema.json` | 该渠道结构指纹汇总（事件类型集合、各级字段集合、字段顺序、has_ping） | 直接 diff 两个 schema.json 最快看出差异 |
| `raw/req_NN.json` | 第 NN 个请求体（pretty JSON，字节级） | 需要看完整 prompt/tools 时 |
| `raw/resp_NN.sse`/`.json` | 第 NN 个响应原始体（`.sse`=流式，`.json`=非流式） | 逐响应字节级 diff |

| 2 | A#2 98965B | B#2 98965B | |
| 3 | A#3 99414B | B#4 99414B | 顺序在B里靠后 |
| 4 | A#4 872B | B#3 872B | 小请求(1 tool)，**两边都返回非流式 JSON 响应** |
| 5 | A#5 99246B | B#5 99246B | |

> → **输入完全对齐**，下列响应差异全部归因于"渠道/上游"。

## 结构指纹并排对比（A 原生 vs B-Vertex）

- A 有 ping: **True**　B 有 ping: **False**
- A `message_start.message` 字段顺序：`model, id, type, role, content, stop_reason, stop_sequence, stop_details, usage`（原生固定序）
- B `message_start.message` 字段顺序：`content, id, model, role, stop_reason, stop_sequence, type, usage`（字母序，被重新序列化）
- A event 计数：`message_start:6, content_block_start:36, ping:7, content_block_delta:193, content_block_stop:36, message_delta:6, message_stop:6`
- B event 计数：`message_start:8, content_block_start:15, content_block_delta:728, content_block_stop:15, message_delta:8, message_stop:8`

| 维度 | A 独有（B 缺） | B 独有 |
|---|---|---|
| event 类型 | **ping** | — |
| message_start.message 字段 | **stop_details** | — |
| message_start.usage 字段 | **cache_creation, cache_creation_input_tokens, cache_read_input_tokens, inference_geo, service_tier** | — |
| message_delta 字段 | **context_management** | — |
| message_delta.usage 字段 | **cache_creation_input_tokens, cache_read_input_tokens, iterations, output_tokens_details, server_tool_use** | — |
| content_block 类型 | server_tool_use, web_search_tool_result | — |

> 关键：差异是**单向**的——A（原生）拥有 B 的全部字段且更多，B 没有任何 A 缺失的字段。
> 即 B 是原生响应的"降级子集"。
> 注：`content_block` 的 `server_tool_use`/`web_search_tool_result` 仅因 A 本次恰好触发了一次联网搜索，
> 属任务相关；但也说明原生 envelope 支持 server-tool，B 这套未观察到。

## 建议的程序对比方法
1. 最快：`diff <(jq -S . export/A/schema.json) <(jq -S . export/B/schema.json)`
2. 逐事件：对 `events.jsonl` 按 `event` 分组，比较每类事件的 `data` 字段键集合。
3. 字段顺序：只有原始字节能体现（JSON 解析会丢顺序）——看 `raw/resp_NN.sse` 里 `message_start` 那行的键序。
4. 缓存行为：在 `events.jsonl` 里筛 `message_start`，看 `data.message.usage.cache_read_input_tokens`
   是否随轮次出现（A 有，B 恒缺）。

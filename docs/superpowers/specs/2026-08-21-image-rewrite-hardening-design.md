# 图片回程改写资源边界设计

## 目标

修复图片超分、尺寸规整和输出转码中的多图内存峰值、响应数量扫描和混合交付问题，同时保持现有产品行为：`n` 不设置本地图片数上限，按配置并行调用 worker，整批成功或整批降级，超大上游响应原样透传。

## 保持不变的行为

- 超分资格不再设置固定图片数上限；本地同时在飞任务由 `IMAGE_UPSCALE_MAX_CONCURRENCY` 控制，允许上限为 200。
- 上游响应超过 96 MiB 改写上限时跳过本地改写，完整透传已付费结果。
- 改写后的最终响应同样不得超过 96 MiB；超过时丢弃中间结果并完整透传上游响应。
- 响应图片数量必须等于请求 `n`；校验失败不得调用 worker。响应总大小仍受 96 MiB 改写上限约束。
- 多图请求共享一次 `IMAGE_UPSCALE_TIMEOUT`，该配置继续表示整批请求预算。
- 任一放大、规整、编码或 JSON 组装步骤失败时，丢弃本批全部中间结果，由 handler 返回原始上游响应。
- 客户端请求 `jpeg` 或 `webp` 时，成功结果中的每张图片必须使用同一编码；未指定或请求 `png` 时统一输出 PNG。

## 根因

当前实现虽然逐张执行 worker，但每张图片都会调用多次 `sjson.SetBytes`。每次调用都可能复制不断增大的整份 JSON；第四张 4K 图片写回时，旧响应、新响应、PNG 和 base64 会同时驻留。响应数量检查还会调用两次 `gjson.Result.Array()`，在判断上限前为全部数组元素分配切片。尺寸规整则把“不适用”和“已满足目标”都表示为 `changed=false`，导致部分图片被改写、部分图片原样保留。

## 设计

### 有界响应检查

新增统一的响应检查函数，通过 `gjson.Result.ForEach` 遍历 `data`，只保存每个条目的必要字段；不设置固定图片数上限。检查阶段同时验证：

- `data` 是非空数组；
- 条目数等于请求 `n`；
- 每个条目存在非空 `b64_json`；
- 单张 base64 长度不超过现有 64 MiB 解码预算。

检查结果只保存必要的 `gjson.Result` 和字段偏移，不复制整份图片数组；后续处理使用有界 worker pool。

### 分段 JSON 组装

用分段响应对象替代循环调用 `sjson.SetBytes`。组装器收集不重叠的 JSON 替换区间，按原文偏移排序后生成以下片段：

- 未修改区间直接引用原响应字节；
- `size` 和 `output_format` 使用短静态片段；
- `b64_json` 使用对应图片最终编码后的单个 base64 片段。

组装器逐张追加片段，但在全部处理成功前不向客户端暴露结果。最终响应片段总长度实时累计，超过 96 MiB 时立即终止并触发整批降级。整个请求只保留原响应、受 96 MiB 上限约束的最终响应片段以及当前正在处理的一张图片，不再为每张图片复制整个 JSON。

最终响应大小仍由图片数量决定，这是协议本身不可消除的成本；修订后它有明确总上限，额外工作集不再出现反复复制整份响应造成的二次增长。

### 响应处理器复用

分段响应体实现普通 `io.ReadCloser`，同时暴露原始响应作为 usage 解析来源。OpenAI 兼容图片响应处理器识别该接口后：

- 从原始响应解析 `usage`，不扫描改写后的大图片字段；
- 直接把分段响应体写给客户端，不再对改写结果执行第二次 `io.ReadAll`；
- 继续复制既有响应头、设置准确 `Content-Length` 和 payload-written 标记。

未识别该接口的 adaptor 仍可把它当普通响应体读取，保持兼容性。只有已经通过 OpenAI `data[].b64_json` 预检的响应才会进入成功改写路径。

### 原子处理

所有字段偏移和图片头信息在调用 worker 前完成预检。分段结果只在全部图片处理成功后交给 handler；中途失败或最终结果超过 96 MiB 时直接丢弃片段，原始响应仍保持完整，可用于降级。

超分路径对每张图片执行：读取原图、调用 worker、转换为目标编码、生成最终 base64 片段。图片任务通过有界 worker pool 并行运行，worker 数量为 `min(n, IMAGE_UPSCALE_MAX_CONCURRENCY)`；任务结果按原索引收集，保证响应顺序稳定。上游 RunPod 的队列和自动扩容继续负责远端容量，new-api 只限制本地同时在飞任务。

尺寸规整路径先对全部图片分类：

- 尺寸不一致且格式、位深、尺寸均可处理：执行重采样；
- 尺寸一致但编码不符合整批目标：只做本地转码；
- 任一图片格式不支持、头部扫描超限、16 位或尺寸越界：整批判定为不适用，原样透传；
- 全部图片尺寸和编码均已满足目标：零成本原样返回。

因此成功响应不会出现混合尺寸、混合编码或与顶层声明不一致的条目。

### 转码失败语义

沿用当前整批原子设计：转码失败视为本批改写失败，由 handler 返回原始上游响应。旧测试中“保留 worker 产出的 PNG”属于上一版单图降级语义，需要更新为整批降级契约。

## 测试

- 大量响应条目不会触发固定数量拒绝；worker 调用数量受配置并发池限制。
- 多图改写验证并行任务确实同时运行，且最终响应保持原索引顺序。
- 任一任务失败会取消同批剩余任务，且不暴露部分结果。
- 多图改写只产生图片 base64 片段，不调用 `sjson` 复制整份响应。
- 改写结果累计超过 96 MiB 时整批降级，原响应字节保持不变。
- OpenAI 兼容响应处理器不会对分段改写结果再次执行整块读取。
- 第二张 worker 或转码失败时不暴露第一张的部分改写结果。
- 规整响应包含“已满足目标”和“需要规整”的 JPEG 时，最终全部为 PNG 或客户端要求的统一格式。
- 任一规整图片不适用时整批原样返回。
- 已有超限响应透传、精确数量校验、并发限制和 race 测试继续通过。

## 非目标

- 不改变超分模型、图片档位映射、计费模拟或渠道能力过滤。
- 不改变尺寸、单图字节数或 96 MiB 响应上限；并发上限由 `IMAGE_UPSCALE_MAX_CONCURRENCY` 控制，最大 200。
- 不改变 RunPod、S3 临时对象和清理流程。
